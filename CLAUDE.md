# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

sashimi (PyPI distribution **`sashimi-convert`**, import name `sashimi`) is a Python ≥3.11 library for file conversion and video contact sheets, built on FFmpeg/ffprobe (system binaries on `PATH`) and Pillow. It is the conversion engine behind FileSushi's sandboxed workers and the basis of a desktop app, and ships a Typer CLI (`sashimi`, entry point `sashimi.cli:main`, needs the `[cli]` extra). Uses `uv`; hatchling (≥1.27, for PEP 639 licence metadata; both targets pinned to core metadata 2.4) builds; the version lives only in `src/sashimi/_version.py`, and the first `## ` heading of `CHANGELOG.md` must match it (`tests/test_metadata.py`). `CHANGELOG.md` must record every Python API break (pre-1.0, breaks are allowed), with upgrade steps in `MIGRATION.md`; `docs/FILESUSHI_HANDBACK.md` documents the contract FileSushi depends on, and `tests/core/test_filesushi_contract.py` pins the parts of it that aren't field definitions. `CLAUDE.md` and the handback stay out of the sdist (`[tool.hatch.build.targets.sdist]`) and the wheel. The owner builds and uploads releases by hand; never publish, tag or add a publishing workflow.

Licensing: Apache-2.0, copyright "The FileSushi Authors" (listed in `AUTHORS`). Every hand-written source file (`.py`, `.sh`, `pyproject.toml`, the sandbox `Dockerfile`) starts with the two lines `# SPDX-FileCopyrightText: 2026 The FileSushi Authors` / `# SPDX-License-Identifier: Apache-2.0` (after a shebang if there is one); `tests/test_licensing.py` fails on a tracked or new file without them. Keep `LICENSE` verbatim; there is no `NOTICE`.

## Commands

```sh
sh scripts/check.sh                 # ruff format --check, ruff check, mypy, pytest on 3.11–3.14; run before handing work back (there is no CI)
uv run pytest tests/core/test_video_commands.py::test_gif_defaults    # single test
uv run pytest tests/core            # fast unit tests, no ffmpeg needed
sh scripts/sandbox_check.sh [--skip-long]   # every converter in a FileSushi-style locked-down Alpine container (needs Docker)
uv run sashimi thumbs <path> -r     # run the CLI
```

`check.sh` changes nothing: `uv run --frozen` (never re-locks) with `UV_PROJECT_ENVIRONMENT=.venvs/<version>` (override the parent with `SASHIMI_CHECK_VENVS`), so `.venv` and `uv.lock` are left alone. Ruff line length is 120; `F401` is ignored. Integration tests (`tests/integration`, some `tests/cli`) generate media at test time with lavfi `testsrc2`/`sine` (fixtures in `tests/conftest.py`, inputs named `original.blob`) and skip without ffmpeg. `tests/conftest.py` silences Pillow's DEBUG logger: with pyproject's `log_cli` at DEBUG, log records inside typer's `CliRunner` close its captured output on Python 3.11.

## Architecture: three layers

1. **Core** (`sashimi/core/`, re-exported by the public faces `sashimi.video`, `.audio`, `.image`, `.sheets`, `.metadata`, and `sashimi.probe`/`sashimi.errors`). Single-file functions `(input_path, output_path, config, *, max_workers, scratch_dir, limits, on_progress)`; the Pillow-only functions (`image.convert`, `to_ico`, `favicon_pack`, `edit`, `select_frames`, `frame_strip`, and `frames_info(path, *, limits)`) take no `max_workers`, and `sheets.render` adds `display_name`, `header_font`, `timestamp_font` and `emoji_dir`. Hard rules, because FileSushi runs them in a read-only, no-network, `pids_limit=128` container:
   - never derive outputs from inputs, `.resolve()`, or look at extensions; detect input type by content (`core/probe.py` via ffprobe JSON, or Pillow) and take output format from the config (`-f <muxer>`);
   - write via `core/_atomic.atomic_output` only; pipe frames (raw RGB over stdout/stdin) instead of temp files;
   - no config files or network, and nothing written under `HOME` (pilmoji emoji only from a local `emoji_dir`). One read under `HOME` remains: without `header_font`/`timestamp_font`, sheets try system font names (`core/sheets/_render._FONT_CANDIDATES`), and Pillow's `ImageFont.truetype` also searches per-user font folders (`~/.local/share/fonts`, `~/Library/Fonts`), so sheet text depends on the host's fonts; pass font paths for repeatable output;
   - bound threads: `core/_resources.resolve_max_workers` (default `min(4, CPUs)` honouring cgroup quotas); every ffmpeg call gets `-filter_threads` through `base_args()`, and every decode and encode gets `-threads`. The exceptions: ffprobe gets neither; copy trims and remuxes (no decode or encode, `base_args(1)`), the animated-GIF sheet encode and the preview's GIF encode get no `-threads`;
   - enforce only the caller's limits (see "Limits" below): no fixed upper limit in core, the batch API, the CLI or a config field;
   - **the metadata rule:** every output that can carry the source's metadata has one `metadata` field (`MetadataMode`: `keep`, the default, `remove_location`, `remove_all`; in `config/_base.SourceMetadata`), and it alone decides what the output keeps (`keep_icc` decides the colour profile alone). Never let Pillow or ffmpeg copy metadata by default: images read their carriers from the file (`core/_imagemeta.read_carriers`), apply the mode (`apply_mode`) and write them explicitly (`save_arguments`), and are saved through `clean_info` (Pillow's writers copy `info` and a TIFF's tags); ffmpeg commands get `core/_mediameta.metadata_args` and `dropped_streams` from the probed `source`. `keep` carries everything the format holds; `remove_location` removes every carrier in the README's "Metadata" list; `remove_all` keeps only what display or playback needs (orientation when not applied, stream languages, display rotation). Applying the orientation resets it to 1 and drops the EXIF thumbnail. EXIF is edited in place (`core/_tiffmeta.py`) so maker notes keep their offsets. `sashimi.metadata` reads a file's metadata (`read`, no decoding) and removes it without re-encoding (`strip`). A new carrier or output goes into the byte-level tests (`tests/core/test_metadata_images.py`, `tests/integration/test_metadata_media.py`, fixtures in `tests/metadata_samples.py`), with synthetic values only;
   - raise `UserInputError` subclasses (with a plain-sentence `.user_message`) for user-fixable problems and `ProcessingError` otherwise; callers branch on type, never message text. Code that turns a `ProcessingError` into a user error or a skipped frame (`probe()`, the sheet frame grabs) must re-raise `BinaryNotFoundError` first, so a missing ffmpeg/ffprobe is never reported as bad media.
   All ffmpeg runs go through `core/_ffmpeg.run_ffmpeg` (progress parsing, stdin feeding, stderr tail). Command builders (`build_*_command`) are **pure** and pinned argument-for-argument by parity tests (`tests/core/test_*_commands.py`); changing an argument is a FileSushi-visible change. Every output gets `OUTPUT_FLAGS` (`-fflags +bitexact`) so results are byte-identical; inputs get `INPUT_PROTOCOLS` (`-protocol_whitelist file -format_whitelist <VIDEO_CONTAINERS | AUDIO_CONTAINERS>`, both sets defined in `core/_ffmpeg.py`) and must pass the container allowlists re-exported by `core/probe.py`. Every re-encode gets `-t`: the requested length, or the probed remainder plus `DURATION_TOLERANCE_SECONDS`, capped at `limits.max_video_seconds` (`max_audio_seconds` for audio) when one is set. Outputs come from `atomic_output` with mode 0666 minus the umask.
   Config models live in `sashimi/config/` (FileSushi's web app imports it, so it may import only pydantic and `sashimi.errors`; `tests/core/test_config_module.py` pins that). One model per operation and output format, holding only fields that affect that output, with concrete defaults (`None` only for "keep the source's value"/"to the end"); field bounds are only format and codec limits and correctness rules (`tests/core/test_config_module.py::FORMAT_UPPER_BOUNDS` lists every upper bound allowed), and cross-field rules raise `sentence(...)`. Models subclass `ParamsModel` (frozen, `extra="forbid"`, `use_attribute_docstrings`, finite numbers only, `None` → default, `from_params(params, **fields)` → `InvalidOptionsError`); every field needs a user-facing docstring right under it, which becomes its `description` (FileSushi form help, `sashimi config defaults`; `test_every_field_is_described` pins it); each operation's `ConfigFamily` (`IMAGE_CONVERT`, `VIDEO_TRIM`, `CONTACT_SHEET`, …) picks the model. Field names match FileSushi's form fields; server paths (fonts, `emoji_dir`) are function arguments, never fields.
   **Limits** (owner rule below): every limit is the caller's, in one frozen `sashimi.config.Limits` (`config/_limits.py`: `max_pixels`, `max_frame_bytes`, `max_animation_bytes`, `max_sheet_pixels`, `max_video_seconds`, `max_audio_seconds`, `max_gif_seconds`, `max_preview_clips`; each a number or `None` for none; `Limits.unlimited()`). Every core function, command builder and batch function that can meet one takes `limits: Limits | None = None` and starts with `limits = resolve_limits(limits)` (`None` → the defaults: 64 MP images and sheets, 1 GiB of decoded frames, no length limits). Limits a config breaks by itself are its `_check_limits(limits)` hook, reached through the public `limits.check(config)`, which converters and builders call before probing (and a web app at queue time); file-dependent checks follow in core. Refusals state the limit in force (`config._limits.duration_text`, `megabytes`, `megapixels`) and set `UserInputError.limit` to the field name. A new limit is a new `Limits` field with a sensible default (one that protects the machine; no default length limit) plus a `KINDS` entry in `cli/_limits.py`, and a `--max-*` flag only if users meet it at the default. Keep a fixed bound only for a format or codec limit or a correctness rule (`MIN_FRAME_MS`, `MAX_ANIMATION_FPS`, `MIN_TILE_SIZE`, `WEBP_MAX_SIDE`), and add it to `FORMAT_UPPER_BOUNDS`. Pillow's own pixel limit is raised under a lock in `core/image._pillow_allows` when `max_pixels` exceeds it.
   Contact sheets: `core/sheets/__init__.render` dispatches to `static.py` (frames via a thread pool of single-threaded ffmpeg) or `animated.py` (clips decoded to raw frames, composited with Pillow, encoded by one ffmpeg; no moviepy); `_layout.py` is pure grid/timestamp maths plus the tile-size check, `_render.py` draws header/labels with local fonts.
2. **Batch API** (`sashimi/api/`, lazy `__getattr__` exports). `_batch.run_batch` returns a `Batch` (an iterator over the result protocol, plus `plan()`): it discovers files by extension, plans every output and outcome before anything is written (`BatchPlan`/`PlannedFile`: output, action `write|replace|exists|skipped|error`, kind, route), handles `exists`/`force`, and maps exceptions to statuses by type (`classify`). The policy is in the `_batch` module docstring and the README ("Where outputs go", "Folders of mixed files"); naming mechanics are in `api/_naming.py`, earlier-output recognition in `api/_outputs.py`, kinds and messages in `api/_kinds.py`. Rules (owner, 2026-10-21):
   - **Determinism:** an output's name depends only on its own input path, the command and the settings, never on the other files in the batch (the 0.6.0 rule that renamed colliding inputs made "exists" depend on what sat next to a file).
   - **Patterns** (`NameTemplate(text, origin)`; fields `{input_name}` `clip.mp4`, `{input_stem}` `clip`, `{input_ext}` `mp4`, `{role}` `sheet`, `{output_ext}` `jpg`; `{{`/`}}` literal; no aliases for old names): every command's default is `{input_name}.{role}.{output_ext}` (`photo.jpg.rotated.png`), conversions (`convert`, `remux`) `{input_name}.{output_ext}`; `default_output_name(command)`. `{output_ext}` is the extension the caller typed (`output_ext=`, `convert`'s target as given, `--output-format`), else the input's own as written when the format is kept, else the standard one (`_naming.output_format`). A literal extension must name the output's format: refused up front (`naming(..., fixed=)`) when every output has one format, else a per-file `error`. `output_name` (API) / `--output-name` / `output_name` in the command's `sashimi.toml` section replaces the default; each planned name is checked (`_naming.check_name`: one component, valid on Windows and POSIX except for characters the input's name has, at most 255 characters).
   - **A run never processes its own outputs, and nothing more (owner, 2026-10-21):** a directory search leaves out only the files this command, with these settings (its pattern and output format), would name from another file found anywhere in the search, so outputs written with `output_dir` count too (`_outputs.own_outputs`; a name that is just another file's stem with a new extension counts only in that file's folder; files that would each be named after the other are both originals). Everything else found is processed, other commands' outputs and the same command's under other settings included: "if I ran that command, I'd expect it to convert those JPEG files to `webp` files. Why would I expect anything else?" Files named together count the same way (sashimi agent, 2026-10-21, awaiting the owner's confirmation: a shell glob such as `resize *.jpg` names the run's earlier outputs alongside their originals, and a rerun made `a.jpg.resized.jpg.resized.jpg`); a file named on its own is always processed. The plan lists what was left out. There is no cross-command recognition and no `include_outputs`/`templates`.
   - **Clashes:** inputs whose outputs would share a name (compared case-insensitively) are all `skipped`, with or without `force`; each message names the other inputs and the shared name ("Clashes with x.mp4: both would be named x.jpg."), and when the pattern caused it `BatchPlan.clash_note` names the pattern and its origin once (the CLI prints it at the end, the report has `clash_note`). Never suggest `-f`.
   - **`force` replaces whatever is in the way**, the input itself included (`{input_name}` edits in place); outputs are always staged and moved into place; an input another output will replace is processed first (`_batch._order`). Without `force`, "exists" says what sashimi knows (`_exists_message`: the input, another input, a name a pattern gives originals, or an earlier output).
   - **Routes:** each batch function passes `route=` naming the code each file goes through (`rotate_files`: `edit` for images, the same `core.edit` as `edit --rotate`, and `transform` for videos; `convert_files`: `route_for`; `strip_files`: `image`/`media`). `BatchPlan.mixed` (more than one route) is what the CLI asks about; the API never prompts. Unsupported files get `accepts=` in the message ("thumbs works on videos, not .jpg files").
   - **Where outputs go (owner, 2026-10-21: "I agree, this is much cleaner"):** next to each input; a folder beside each input is said in the pattern (`sheets/{input_name}.jpeg` → `New folder/sheets/Bluebeard-5.mkv.jpeg`, from any folder; folders made as needed; `\` is a separator on every system; absolute paths, drive letters, `~`, `.`/`..` and empty folder names refused, pointing at `output_dir`); `output_dir` is one folder with ordinary path meaning (relative to the current folder, same for the flag and the kept setting), keeping the subfolders below a searched directory, with the pattern's folders below those; `output` names the one output for one input (bypasses the pattern, must end in an extension of the output's format). Files a search finds inside `output_dir` are left out (`BatchPlan.in_output_dir`) unless `output_dir` holds the searched folder; named files never are. Messages name an output by its file name when it's beside its input, else by its path as built (`_batch.shown`). `tests/api/test_naming.py` pins names and patterns, `tests/api/test_invariants.py` pins, for every batch command and default, short and literal patterns, determinism, idempotent reruns (also with `output_dir` in a subfolder, a nested folder and a sibling), that for every ordered pair of commands the second processes each of the first's outputs it takes exactly once and never its own, no silent loss with and without `force`, and honest "exists"; `tests/cli/test_regressions.py` holds one test per bug found in real use. Every new batch function follows it: build a `_naming.naming(command, format_for, output_name, fixed=)` and pass it with `accepts` and `route` to `run_batch`, and add the command to `_naming.COMMANDS`/`ROLES` and the invariant tests. Results: per file `(path, "starting", message, output)` then `(path, status, message, output)` with status `success | error | exists | skipped` (`ResultTuple`), after the file count and rejected inputs. `_consume.consume_generator` turns that into the report (with `kinds`, `routes` and `outputs_left_out`; optional tqdm).
3. **CLI** (`sashimi/cli/`). `resize` and every other processing command take several paths; `convert` takes them as `PATH... FORMAT` (`_options.paths_then_format`: the last argument is always the format, with a note when a file or folder here has its name; `--output-format` instead) and `rotate` as `PATH... [ANGLE]` (`_options.paths_then_angle`: a last `0`/`90`/`180`/`270` is the angle unless a file or folder here has that name, which is refused; `--angle` instead); `extract` takes one video. A named file already in the output's format ("Already JPEG", `BatchPlan.already_done`) exits 0; `frames` with nothing to change is refused. `config defaults` prints its tables, or one block per option when the columns can't fit the terminal without cutting a value (`config_cmd._widths`). `main.py` builds the Typer app (`--version`, help panels, `no_args_is_help` on every command that takes arguments) and registers `convert`, `resize`, `rotate`, `edit`, `frames`, `favicon`, `extract` (hidden alias `trim`), `remux`, `strip`, `thumbs`, `preview`, `info`, `metadata`, `flatten` and `config`, from `convert_cmd.py`, `edit_cmd.py`, `thumbs_cmd.py`, `files_cmd.py`, `metadata_cmd.py` and `config_cmd.py`. `--metadata` (the `metadata` field) is on every command whose models have it. Every processing command prints the same `--json` report (`schema`, `command`, `summary`, `results`); `info` and `config` keep their own JSON shapes. All logging goes to stderr. `-o/--output` is always the output file, `--output-format` (no short flag) the format, spelled as the extension to write (`jpeg` or `jpg`; `convert` takes it as an argument), `-y/--yes` answers questions (`-f` implies it), `--duration` an output length and `--clip-length` a sampled clip's length; `-h` is help everywhere. Shared option declarations live in `_options.py` (one `Annotated` alias per flag, grouped into help panels), and `_output.BatchRunner` renders batch progress (including per-file progress via `on_file_progress`) and results/JSON. Commands import heavy modules inside the function body so `--help` stays ~0.2 s; keep it that way. When adding a config field, expose it as a flag too, add it to the command's `FLAGS` map, and give the flag a `[default: …]` note matching the model; `tests/cli/test_help_defaults.py` checks every note against the model defaults. Declare options with `_options.option(...)`, which escapes `[default:` (Rich would otherwise read it as a markup tag and delete it); a bare `typer.Option` help must not contain `[default:` or other lowercase `[...]`. `_defaults.py` formats defaults, accepted values and `sashimi.toml` overrides for `sashimi config defaults <command> [format]` (whose first table is always "Output names", `name_rows`) and for `thumbs --help` (`thumbs_cmd.ThumbsCommand` annotates help with TOML values at render time; `settings.read_config()`). `settings.py` is the only code that reads/writes TOML (your own `~/.sashimi/sashimi.toml`, and the project `sashimi.toml`/`.sashimi.toml` found from the current folder upward, which wins there; **`config set`/`unset` write your own file by default** (owner, 2026-10-21: a pattern set with the old project default inside `New folder` was ignored from the folder above), `--project`/`-p` the project file that applies here (or `./sashimi.toml`), and both print the file they changed; a new file starts with a comment (`settings.USER_HEADER`/`PROJECT_HEADER`); a file that isn't valid TOML is never rewritten (`settings.SettingsFileError`); the sections are `[thumbs]`, `[animated_thumbs]`, `[limits]`, and one per processing command (`settings.NAMED_SECTIONS`) holding only `output_name` and `output_dir` (`settings.OUTPUT_KEYS`), which `[thumbs]` and `[animated_thumbs]` also take, each for its own sheets; the dead `[global]` settings were removed in 0.6.0); `_options.naming_args` gives every batch call `output_name` (`--output-name` > the command's own `sashimi.toml` section > the default, each a `NameTemplate` with its origin; a broken pattern in that section is exit 2, other sections aren't read), and refuses `--output-name` with `-o`; `_options.output_dir_args` gives `output_dir` (`--output-dir` > `--no-output-dir` (next to the inputs) > the section's `output_dir` (`~` expanded) > none; `-o` ignores a kept folder and refuses the flag); `_options.KeptCommand` (every processing command's class; `thumbs_cmd.ThumbsCommand` extends it) adds the section's kept `output_name`/`output_dir` to `--help`; `--output-name` is for one run, and its help says `sashimi config set <section>.output_name` keeps one (owner: "A user should persist via the `sashimi config set` command"); `_output.BatchRunner` asks about mixed folders (`Batch.plan().mixed` on a directory run; `_output.every` words the count: "both", "all 3") on stderr unless `yes`, stops with exit 2 without a terminal, shows counts in a dry run, and sorts problems first; `_limits.py` turns the `--max-*` flags (in the "Limits" help panel, only on commands whose default limits users meet) and `[limits]` into a `Limits` (`_limits.resolve(**flags)`: defaults < `[limits]` < flags; values like `200M` pixels, `4G` bytes, `10m`, or `none`), which every processing command passes to its batch function, and `sashimi config defaults limits` lists them; only `sashimi config set` creates or writes a file, never a normal run, and built-in sheet defaults come from the models, not a TOML template (a written template pins old defaults). `settings.known_keys` is the one list of keys each section accepts: `config set` refuses others, and `load_raw_config` warns once per run about any in a file (help stays silent). Old key names are never translated (owner, 2026-10-21: "the tool has no users. Nothing needs translating"), so 0.2-era keys get the warning; it turns the path keys (`header_font_path`, `timestamp_font_path`, `emoji_dir`) into `sheets.render` arguments. Flags a chosen model doesn't have are dropped with a warning (`_options.split_options`, `_output.warn_unused`).

## Owner decisions that shape new work

- **sashimi powers FileSushi Desktop,** so any behaviour FileSushi or the desktop app should share belongs here, not in FileSushi's worker (owner, 2026-10-20).
- **One operation per thing the user wants; sashimi picks the route.** For example, converting to MP4 should stream-copy when the codecs allow and re-encode otherwise, without the caller choosing. Don't expose implementation routes as separate tools or options (owner, 2026-10-20).
- **Not wanted:** a two-input mux (ftool's `--merge-split`), and anything that deletes a source file (ftool's `--cleanup`) (owner, 2026-10-20).
- **Limits are configuration.** "All limits should be config driven, so there's no reason to add upper limits to any of sashimi's commands unless there are seriously good reasons to do so. The sashimi defaults don't need to be aligned with filesushi at all, sashimi just needs to be configurable." Memory budgets such as the animation frame budget are "a *filesushi* concern. Sashimi should have sensible defaults but it should be possible to run it at higher settings." So: every limit has a sensible default that can be raised or turned off, no fixed upper limit without a seriously good reason (a format or codec limit, or a correctness rule), and sashimi's defaults needn't match FileSushi's, which sets its own (owner, 2026-10-20). How limits reach core is under "Limits" above.
- **Metadata: capability with permissive defaults.** "In sashimi? keep, of course, but it must be *capable* of full and partial removal." One `metadata` field with `keep` (default), `remove_location` and `remove_all` on every output that can carry metadata, a read call for UIs and a lossless removal; FileSushi chooses its own default ("Remove location metadata") and passes it (owner, 2026-10-20). See the metadata rule under "Architecture".
- **Output names (owner, 2026-10-21):** every output's name includes its input's whole name; users set the pattern and keep it in `sashimi.toml` ("just as long as I can keep it in my sashimi.toml"); old settings are never translated. Fields: "`input_name` and `input_stem` and `input_ext` must all be available possibilities. `role` can remain. `output_ext` should replace `ext`." The default for every command is `{input_name}.{role}.{output_ext}` (conversions `{input_name}.{output_ext}`), and `--keep-extension` is gone. A format the user typed is the extension (`convert . jpeg` writes `.jpeg`). See the naming policy under "Architecture".
- **Routing by media type lives in the API (owner, 2026-10-21):** "The CLI layer has no business being anything more than presentation calling a separate API layer which is fully coherent and useful by itself." `rotate` takes images (through the same code as `edit --rotate`) and videos; `resize` is images-only for now; unsupported-file messages name what the command takes.
- **Mixed folders ask first; `-f` just does it (owner, 2026-10-21):** a directory run whose files would take different routes in the Python layer asks ("this folder contains 44 videos and 23 images…"), `-y` answers, and "`-f` must imply `-y`". "`-f` is a command that users expect to 'just do it'… If the problem is 'I am refusing to do this because of conflict A' then `-f` must never also say that": `-f` replaces anything on disk, the input included. Two outputs of one run with one name are skipped, with or without `-f`, and the message blames the pattern; "the final results table should surface the problems at the top". Tests must catch this kind of bug: "stuff like this needs to be caught by unit or regression tests otherwise the suite is worthless."
- **Check outcomes, not just the spec (owner, 2026-10-21).** The 0.6.0 naming bug came from a rule that was specified, accepted and built exactly, and nobody ran it the way a user would. Exercise what you build as a user would (rerun on the same folder, on a subfolder, after adding or removing files, with existing outputs, odd names, Windows-style paths) and look for non-determinism, duplicates, data loss and surprises. If an instruction, a brief or an owner decision leads to a bug or a bad outcome, don't build it as written: build the safe alternative if it's clear, otherwise leave it undone, and report it with a concrete example.
- **The first PyPI release is 0.6.0.** Image editing, frame selection, the caller's limits and the metadata setting are in, and the known bugs are fixed, so 0.6.0 is complete; it waits for the owner's review and upload (2026-10-20). Keep the version at 0.6.0 and extend its changelog entry until then.
